# 01 需求方案

> 题目原文：*"要求做一个包含预定功能、订单查询、办理入住的带前后端的酒店系统"*

## 1. 需求澄清：一句话需求中的歧义与本方案的假设

一句话需求有大量隐含歧义。真实工作中我会向产品提出以下问题；面试语境下无法问答，故每条均给出**本方案采用的假设与理由**：

| # | 澄清问题 | 本方案假设 | 理由 |
|---|---|---|---|
| 1 | 单店还是连锁多店？ | 单店 | 库存模型设计为"房型 × 日期"粒度，扩展多店时只需加 `hotel_id` 维度，模型不推翻 |
| 2 | "预定"是否包含支付？ | 含**模拟支付** | 支付是订单状态机的核心环节；预留真实支付网关回调接口位 |
| 3 | 是否需要登录/会员体系？ | 游客下单，手机号查询 | 题目未提；手机号即订单的弱凭证，与酒店行业"到店凭身份证/手机号入住"一致 |
| 4 | "办理入住"的主体？ | 前台（面客操作） | 入住办理是前台职责，客人侧提供订单查询与取消 |
| 5 | 房量管理的粒度？ | 房型 × 日期 | 酒店库存的本质是"某晚某房型可售量"，这是防超卖正确建模的前提 |
| 6 | 取消策略？ | 占房状态（待支付/已确认）可取消并释放库存 | 取消必须归还库存，否则房态被"幽灵占用" |
| 7 | 演示环境约束？ | 无外网、无外部服务 | 现场演示可靠性第一：H2 文件库、静态前端零 CDN |

## 2. 范围界定（MVP In / Out）

**本期（In）**

1. 房态查询：按入住/离店日期查询各房型可售余量与每晚价格（含周末差异化定价）
2. 预订下单：选择房型、日期、间数，提交入住人信息生成订单（下单即占房）
3. 订单支付（模拟）与取消（取消释放库存）
4. 订单查询：按手机号查列表、按订单号查详情，含完整状态时间线
5. 办理入住/退房（前台侧），含"未到入住日期不可入住"规则
6. 前台今日经营统计：入住/退房/在住/营收/分房型入住率
7. **LOS 收益管理约束**：按"房型×日期段"限制最少/最多连住晚数（MinLOS/MaxLOS），如"国庆档最少连住 3 晚"

**不在本期（Out）与演进方向**

| 能力 | 演进方向（答辩可展开） |
|---|---|
| 真实支付 | 支付网关回调 → 状态机已预留 `pay` 动作位，替换模拟实现即可 |
| 会员/登录鉴权 | JWT + 网关鉴权；手机号查单演进为"会员账号 + 手机号校验" |
| 连锁多店 | 库存表加 `hotel_id` 维度；订单域/库存域拆分微服务 |
| PMS 对接 | 入住/退房动作即 PMS 的 CheckIn/CheckOut 报文位；订单状态机与 PMS 房态双向同步 |
| OTA 渠道（携程/美团） | 中央库存（本系统的 daily_inventory 即其原型）→ 渠道库存分发 + 订单回灌 |
| 促销/优惠券 | 计价策略接口化（`PricingPolicy` 已收敛计价规则，可注入券后价） |

## 3. 用户故事与验收标准

| 编号 | 用户故事 | 验收标准（AC） |
|---|---|---|
| US-1 | 作为客人，我要查询某日期的房态与价格，以便决定预订 | 输入入住/离店日期返回各房型余量与每晚价格；余量=区间内各晚最小值；周末价正确显示 |
| US-2 | 作为客人，我要提交预订生成订单 | 下单成功生成唯一订单号，状态"待支付"，金额=Σ每晚价×间数；房量同步扣减 |
| US-3 | 作为客人，我双击/重试提交不应产生重复订单 | 同一 requestId 重复提交返回同一订单，库存不重复扣减 |
| US-4 | 作为客人，我要支付订单 | "待支付"→"已确认"；重复支付被拒（409） |
| US-5 | 作为客人，我要取消订单 | 占房状态可取消，库存即时释放；已入住订单不可取消 |
| US-6 | 作为客人，我要用手机号查询我的订单 | 输入手机号返回该号码下的订单列表（新单在前） |
| US-7 | 作为客人，我要查看订单状态与过程 | 订单详情含时间线：提交→支付→入住→退房，含操作人/时间/备注 |
| US-8 | 作为前台，我要为到店客人办理入住 | "已确认"订单可办理入住；未到入住日期的订单被拒绝并提示 |
| US-9 | 作为前台，我要办理退房 | "已入住"订单可退房，状态终态"已退房" |
| US-10 | 作为前台，我要看今日经营数据 | 统计卡片展示今日入住/退房/在住/营收/入住率 |
| US-11 | 作为系统，任何并发抢房都不能超卖 | 并发下单时每晚售出 ≤ 总房量（自动化测试证明） |
| US-12 | 作为收益经理，我要对特定日期段设置连住限制 | 区间重叠即生效：少于 MinLOS/多于 MaxLOS 的订单被拒并提示；房态透出最少连住晚数 |

## 4. 非功能需求

1. **并发正确性（最高优先级）**：房量扣减必须原子化，任何并发下不超卖、不重复扣减
2. **幂等性**：下单接口可安全重试
3. **可运行可演示**：一条命令启动（`bash run.sh`），零外部服务依赖，无外网可用
4. **金额精度**：金额一律 DECIMAL/BigDecimal，禁用浮点参与金额运算
5. **可测试性**：领域规则纯函数化；时钟注入，用例与真实日期解耦
6. **迁移友好**：H2(演示) 与 MySQL(生产) 同一套 SQL；代码避免使用 Boot 2 特有 API，预留 Java 17 升级路径

## 5. 与真实酒店业务（华住体系）的映射 —— 答辩要点

- 本系统的 **daily_inventory（房型 × 日期库存）** 就是酒店"中央库存/CRS"的最小原型：真实体系中它对接 OTA 渠道分发（美团/携程实时房价房态接口）、PMS 房态同步
- 本系统的 **订单状态机** 与 PMS 的 Reservation 状态机（预订/确认/在住/离店/取消/NoShow）同构，扩展 NoShow（未到店）只需在迁移表加一条路径
- "下单即占房 + 取消释放"与 OTA 预售模式一致，超时未支付自动释放是生产化第一优先级改造（定时任务扫描待支付超时订单）
