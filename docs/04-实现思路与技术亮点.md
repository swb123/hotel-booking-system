# 04 实现思路与技术亮点总结

## 一、解题思路：从一句话需求到可演示系统的四步法

```
① 需求澄清          ② 领域建模          ③ 实现与验证        ④ 工程化交付
识别歧义、划定范围   状态机/库存粒度/    核心亮点先行、       一键运行、文档、
给出可答辩的假设     计价规则/幂等语义   测试驱动验证         截图、会话记录
(01-需求方案)        (02-技术方案)       (30 用例全绿)       (本仓库)
```

关键判断：**这道题拉开差距的不是 CRUD 完成度，而是"酒店系统真正的技术难点"有没有被识别并被正确解决**——房量防超卖（并发正确性）、订单状态机（业务规则显式化）、幂等下单（分布式系统基本功）。三者全部实现并有测试证明。

## 二、技术亮点（每个亮点：问题 → 方案 → 证明）

### 亮点 1：数据库行锁防超卖（并发正确性）

- **问题**：并发下单时"查余量 → 扣减"之间存在竞态，超卖在真实系统是资损事故
- **方案**：
  - 库存建模为"房型 × 日期"行（`daily_inventory`），并发控制单元=某晚某房型的可售量
  - 下单事务内 `SELECT ... FOR UPDATE` 按日期升序锁定全部占用晚（**固定加锁顺序，杜绝交叉死锁**）→ 锁内校验 `sold ≤ total` → 扣减 → 落单 → 提交
  - H2（MODE=MySQL）与 MySQL 执行同一套 SQL，演示与生产行为一致
- **证明**：`ConcurrencyTest` —— 10 线程抢仅剩 1 间房（2 晚）：**恰 1 单成功、9 单被拒、每晚 sold ≤ total、库中仅 1 笔订单**，断言全部通过
- **双模式（乐观锁追问的标准答案）**：`app.booking.inventory-mode` 可切换——pessimistic（FOR UPDATE 行锁，默认）/ optimistic（条件原子更新 `WHERE sold+n<=total`，零锁等待、冲突由受影响行数判定）；`OptimisticInventoryTest` 以同规格 10 线程场景证明乐观模式同样不超卖。两种模式的对照与生产选择（低竞争乐观、热点 Redis Lua）见 02 §5.3
- **演进纵深（面试加分）**：单库热点 → 按日期分片；秒杀级热点 → Redis Lua 原子扣减 + DB 兜底对账；库存变化 MQ 异步化

### 亮点 2：订单状态机（业务规则显式化）

- **问题**：状态流转散落在 if/else 里会逐渐腐化（已入住还能取消？退房后还能改单？）
- **方案**：`OrderStatus` 枚举内置**显式迁移表**（唯一事实来源）：

```
待支付 ──支付──▶ 已确认 ──入住──▶ 已入住 ──退房──▶ 已退房(终态)
   │                │
   └─────取消────────┴──────▶ 已取消(终态)
```

  - 未声明的迁移一律 409 拒绝（如"已入住不可取消""未支付不可入住"）
  - 守卫规则挂载在迁移动作上（"未到入住日期不可办理入住"→ 400 明确提示）
  - 每次迁移事务内追加 `order_log` 流水（轻量事件溯源）→ 订单时间线、审计、对账一个表搞定
- **证明**：状态机 3 个单测穷举合法/非法路径；HTTP 层 5 个用例覆盖非法迁移、重复支付、提前入住、已入住取消、退房后再入住

### 亮点 3：幂等下单（防重复扣库存）

- **问题**：双击、弱网重试、消息重复投递 → 重复订单 + 重复扣减
- **方案**：`request_id` 前端每次"下单动作"生成一次（`crypto.randomUUID()`，失败重试沿用同一键）+ 数据库唯一索引兜底；命中即返回原订单；并发竞争撞唯一索引 → 事务回滚（含库存）→ 返回"胜者"订单
- **证明**：集成用例 A-02 —— 同 requestId 提交两次，**同一订单号、订单数 1、库存只扣 1 次**

### 亮点 4：领域建模决策（体现对酒店业务的真实理解）

| 决策 | 理由 |
|---|---|
| 库存粒度 = 房型 × 日期 | 酒店卖的是"某晚某房型"，不是"某房型总数" |
| 下单即占房，取消才释放 | 与 OTA 预售一致；避免"支付成功才发现没房" |
| 价格日历（周末上浮 20%）+ 缺失回退基准价 | 计价策略收敛为纯函数 `PricingPolicy`，接券/促销只需扩展该函数 |
| **LOS 收益管理约束层** | MinLOS/MaxLOS 按"房型×日期段"叠加在 Daily 库存之上（对应房价码/RatePlan 维度），区间重叠生效、多规则取最保守并集，锁库存前快速失败 |
| 金额全程 `DECIMAL/BigDecimal` | 禁止浮点参与金额运算 |
| 占房日期序列 = [入住, 离店) | 离店日不占房，与行业间夜数口径一致 |

### 亮点 5：可测试性设计

- **时钟注入**：`Clock` Bean 统一提供"今天"，测试固定为 2026-09-07 → 用例与真实日期解耦，可重复执行
- **领域纯函数化**：状态机/日期规则/计价策略零 IO，秒级单测
- **事务边界显式**：`TransactionTemplate` 声明事务范围，测试能精确控制并发场景
- 30 用例全绿：领域单测 12 + HTTP 集成 17 + 并发 1，一条 `mvn test` 复现

### 亮点 6：演示可靠性工程（现场不翻车的保障）

- **零外部依赖**：H2 文件库（MODE=MySQL）+ 前端零 CDN + 数据内嵌初始化 → 断网也能演示
- **一键启动**：`bash run.sh`（自动定位 JDK → 按需构建 → 启动）；评委机器无 Maven 可用项目自带 `./mvnw`
- **幂等初始化**：重复启动不脏数据；启动自动补足未来 60 天库存/价格
- **双态配置**：`application-mysql.yml` + `docker-compose.yml`，一条命令切真实 MySQL
- **演示数据设计**：四笔订单覆盖全部状态（张伟-今日入住待办理/李娜-在住/王强-今日退房/赵敏-待支付），评委 3 分钟走完全状态流

### 性能基准实测（`mvn test -Dtest=BenchmarkTest -Dexcluded.groups=none`）

| 场景 | 结果 | 解读 |
|---|---|---|
| 串行下单 ×200（日期错开） | **262.7 TPS**，3.81 ms/单 | 业务代码单笔路径开销基线 |
| 并行 ×8 ×200（日期错开） | 19.7 TPS | **受 H2 单写者架构限制**（演示库特性），写事务在库层串行化 |
| 并行 ×8 ×200（同一日期段，行锁竞争） | 19.4 TPS | 与错开场景几乎相同 → 证实瓶颈在 H2 写串行化，而非业务行锁 |

> **如实说明与答辩口径**：H2 为单写者引擎，任何并发写都会被库层排队（这正是上面两个并行场景 TPS 几乎相同的原因）。生产 MySQL 为**多写者行锁**，不同日期段（不同库存行）的订单可真正并行写入，吞吐随连接数线性扩展；热点日期段仍由行锁串行化保证不超卖。**并发正确性不依赖吞吐**——由 ConcurrencyTest（10 线程抢 1 间恰 1 成功）与 DeadlockFreeTest（20 线程交叉锁无死锁）专项保证。如需真实并发吞吐数据，用 docker-compose 起 MySQL 后以 `--spring.profiles.active=mysql` 重跑同一基准即可。

## 四、答辩要点速查（面试官追问预案）

| 可能的问题 | 回答要点 |
|---|---|
| 为什么 Java 8 / Boot 2.7？ | 匹配目标企业存量体系（见 02 §2）；知情决策 + 迁移友好（javax→jakarta 即可升级 Boot 3） |
| 防超卖为什么不用 Redis/分布式锁？ | 单库行锁正确性第一、实现可讲清楚、与 MySQL 生产行为一致；热点场景演进路径已文档化（02 §5.4），量化阈值：**单行 TPS 预估 >5000 时切 Redis Lua + DB 兜底对账** |
| 加锁影响吞吐吗？能不能用乐观锁？ | **已实现双模式可切换**：optimistic=条件原子更新（零锁等待、受影响行数判冲突），与悲观锁各配同规格 10 线程并发测试证明不超卖；对照表与生产选择见 02 §5.3——低竞争用乐观、热点用 Redis Lua、行锁是最简正确基线 |
| 为什么并行基准 TPS 反而低（19 vs 262）？ | 如实回答：H2 是单写者引擎，并发写被库层串行化——这是演示库特性而非业务代码瓶颈；生产 MySQL 多写者行锁，错开日期可线性扩展（04 §三 有实测与解读） |
| 超时未支付订单怎么处理？ | 生产方案：Quartz 每分钟扫描 `PENDING_PAYMENT` 且 `created_at < now-15min` 的订单 → 状态机取消（释放库存）+ 通知；本演示版以手动取消演示同一状态机路径 |
| 支付回调如何保证幂等？ | 状态机已拒绝重复支付（409）；生产方案：支付流水表 `payment_transaction_id` 唯一索引，回调先落流水再驱动状态迁移，重复回调幂等命中 |
| 为什么不用状态机框架？ | 本场景 5 状态 7 迁移，枚举迁移表是零依赖的最简充分解；框架（Spring StateMachine 等）留到多事件源场景再引入 |
| 事务边界为什么放在 Service？ | 编排型用例（下单）用 TransactionTemplate 显式声明；Controller 只做参数校验与响应装配 |
| 幂等窗口过了怎么办（request_id 失效）？ | 唯一索引是数据库层最后防线，不会失效；前端键策略保证"每次下单动作一次" |
| 覆盖率只有 68%，够吗？ | 分层看：领域层 95.5%、配置层 100%（规则全穷举）；控制器/异常分支部分覆盖。集成测试驱动的金字塔 + 关键路径（防超卖/状态机/幂等）全覆盖是重点，盲目凑行数没有意义 |
| 如果评委问华住场景 | 见 01 §5：daily_inventory ↔ 中央库存/OTA 渠道分发，状态机 ↔ PMS Reservation，超时未支付自动释放是第一优先级生产改造 |
