# 04 实现思路与技术亮点总结

## 一、解题思路：从一句话需求到可演示系统的四步法

关键判断：**这道题拉开差距的不是 CRUD 完成度，而是"酒店系统真正的技术难点"有没有被识别并被正确解决**——房量防超卖（并发正确性）、订单状态机（业务规则显式化）、幂等下单（分布式系统基本功）、LOS 收益管理（业务深度）。全部实现并有测试证明。

## 二、技术亮点（每个亮点：问题 → 方案 → 证明 → 演进）

### 亮点 1：数据库行锁防超卖 + 乐观锁双模式（并发正确性）

- **问题**：并发下单时"查余量 → 扣减"之间存在竞态，超卖在真实系统是资损事故
- **方案（pessimistic，默认）**：
  - 库存建模为"房型 × 日期"行：表 `daily_inventory(room_type_id, biz_date, total_rooms, sold_rooms)`，唯一约束 `uk_inventory(room_type_id, biz_date)`——并发控制单元=某晚某房型的可售量
  - 下单事务内 `DailyInventoryMapper.lockByTypeAndDates`（mapper XML）执行 `SELECT ... FOR UPDATE`，`ORDER BY biz_date` **按日期升序锁定全部占用晚（固定加锁顺序，杜绝交叉死锁）** → 锁内校验每晚 `sold_rooms + n ≤ total_rooms` → 扣减 → 落单 → 提交
  - 不足抛 `INSUFFICIENT_INVENTORY`(409)，消息带具体日期与余量（"2026-09-10 房量不足：剩余 0 间，需要 1 间"）
  - H2（MODE=MySQL）与 MySQL 执行同一套 SQL，演示与生产行为一致
- **方案（optimistic，可切换）**：`app.booking.inventory-mode=optimistic` 时走 `DailyInventoryMapper.tryDeduct`——单语句条件原子更新（`UPDATE daily_inventory SET sold_rooms=sold_rooms+n WHERE id=? AND sold_rooms+n<=total_rooms`），零锁等待，冲突由**受影响行数=0** 判定；库存是计数器而非行替换，因此无需 version 字段（比版本号 CAS 更简）。多晚订单逐晚更新，任一行失败由事务整体回滚
- **证明**：`ConcurrencyTest`（悲观）与 `OptimisticInventoryTest`（乐观）**同规格**——10 线程抢仅剩 1 间房（2 晚）：恰 1 单成功、9 单被 `INSUFFICIENT_INVENTORY` 拒绝、每晚 `sold ≤ total` 且最终 = total、库中仅 1 笔订单；另有 `DeadlockFreeTest`：20 线程交叉锁定重叠日期段全部限时完成（证明锁排序防死锁）
- **演进纵深**：单库热点 → 按日期分片；单行 TPS 预估 >5000 时热点日期切 Redis Lua 原子扣减 + DB 兜底对账；库存变化 MQ 异步化

### 亮点 2：订单状态机（业务规则显式化）

- **问题**：状态流转散落在 if/else 里会逐渐腐化（已入住还能取消？退房后还能改单？）
- **方案**：`domain/enums/OrderStatus.java` 枚举内置**显式迁移表**（`TRANSITIONS` Map，唯一事实来源）：

```
待支付 PENDING_PAYMENT ──支付──▶ 已确认 CONFIRMED ──入住──▶ 已入住 CHECKED_IN ──退房──▶ 已退房 CHECKED_OUT(终态)
       │                            │
       └──────────取消───────────────┴────────────▶ 已取消 CANCELLED(终态)
```

  - 未声明的迁移一律 409 拒绝：`INVALID_STATE_TRANSITION`（"订单当前状态为「已入住」，不允许执行该操作"）
  - 守卫规则挂载在迁移动作上（`OrderService.transition` 的 guard 回调）：未到入住日期 → `EARLY_CHECK_IN`(400)；已超过离店日期 → `CHECK_IN_EXPIRED`(409)
  - 每次迁移事务内追加流水表 `order_log(order_id, from_status, to_status, operator, remark, created_at)`（轻量事件溯源）→ 订单时间线、审计、对账一个表搞定
  - 状态流转前 `SELECT ... FOR UPDATE` 行锁读订单（`HotelOrderMapper.selectForUpdateByOrderNo`），并发下同一订单仅一个操作能进入
  - **提前退房释放剩余间夜**：退房时自动释放退房日之后的未住间夜库存（当日及之前视为已消费），同事务完成
- **证明**：`OrderStatusTest` 3 例穷举合法/非法路径；HTTP 层 7 个用例（重复支付 409、提前入住 400、过期入住 409、已入住不可取消、退房后再入住 409、取消释放库存、提前退房释放间夜）
- **演进**：NoShow = 迁移表加 `CONFIRMED → NO_SHOW`（入住日未到店由定时任务驱动）；退款/改期引入支付流水表与变更单，状态机保持单一职责

### 亮点 3：幂等下单（防重复扣库存）

- **问题**：双击、弱网重试、消息重复投递 → 重复订单 + 重复扣减
- **方案（三层防护，各挡一种竞态窗口）**：
  1. **幂等键来源**：前端每次"下单动作"生成一次 `request_id`（`crypto.randomUUID()`，见 `js/app.js` 的 `newRequestId()`），失败重试沿用同一键、成功后清空
  2. **数据库唯一索引兜底**：`hotel_order` 表上的 **`CONSTRAINT uk_request_id UNIQUE (request_id)`**（schema.sql）——即使前端键丢失或被绕过，重复插入也会被数据库拒绝。这是幂等语义的最终防线，不会过期、不会失效
  3. **并发窗口处理**（`BookingService.create`）：① 事务前快速路径 `findByRequestId` 命中直接返回原单；② 事务内二次检查（悲观模式在拿到行锁后、乐观模式在扣减前）挡住"两边同时没查到"的窗口；③ 撞唯一索引 `DuplicateKeyException` → 事务整体回滚（**含库存扣减**）→ 重读返回"胜者"订单
  - 边界：订单号撞 `uk_order_no` 与幂等冲突区分处理——catch 中 requestId 命中→返回原单，未命中→判定订单号冲突、换号重试一次（不会把合法下单误判成 500）
- **证明**：A-02 —— 同 requestId 提交两次：**同一订单号、订单数 1、库存只扣 1 次**；`OptimisticInventoryTest` 验证乐观模式下幂等语义一致
- **演进**：支付回调幂等同理——`payment_transaction_id` 唯一索引 + 先落流水再驱动状态迁移

### 亮点 4：领域建模决策（体现对酒店业务的真实理解）

| 决策 | 理由 |
|---|---|
| 库存粒度 = 房型 × 日期 | 酒店卖的是"某晚某房型"，不是"某房型总数" |
| 下单即占房，取消才释放 | 与 OTA 预售一致；避免"支付成功才发现没房" |
| 价格日历（周末上浮 20%）+ 缺失回退基准价 | 计价策略收敛为纯函数 `PricingPolicy`，接券/促销只需扩展该函数 |
| LOS 收益管理约束层（见亮点 7） | MinLOS/MaxLOS 按"房型×日期段"叠加在 Daily 库存之上 |
| 金额全程 `DECIMAL/BigDecimal` | 禁止浮点参与金额运算 |
| 占房日期序列 = [入住, 离店) | 离店日不占房，与行业间夜数口径一致 |
| 房型与商品的关系（显式标注） | 严格模型中商品（Product）= 房型 × 房价码；单房价码简化下 `room_type` 兼任商品职责（物理属性+销售属性合一），多房价码演进 = 新增 product 表拆分 |

### 亮点 5：可测试性设计

- **时钟注入**：`Clock` Bean 统一提供"今天"（固定 Asia/Shanghai），测试替换为固定时钟 2026-09-07 → 用例与真实日期解耦、可重复执行（`FixedClockConfig`）
- **领域纯函数化**：状态机/日期规则/计价策略/LOS 策略零 IO，秒级单测
- **事务边界显式**：`TransactionTemplate` 声明事务范围，测试能精确控制并发场景
- **同规格双模式测试**：悲观/乐观两套并发测试共享断言口径，策略可切换而正确性证明不降级
- 47 用例全绿：领域单测 21 + HTTP 集成 22 + 并发 4（防超卖×2 模式、无死锁、乐观全流程），一条 `mvn test` 复现

### 亮点 6：演示可靠性工程（现场不翻车的保障）

- **零外部依赖**：H2 文件库（MODE=MySQL）+ 前端零 CDN + 数据内嵌初始化 → 断网也能演示
- **一键启动**：`bash run.sh`（自动定位 JDK → 按需构建 → 启动）；评委机器无 Maven 可用项目自带 `./mvnw`
- **幂等初始化**：重复启动不脏数据；启动自动补足未来 60 天库存/价格；整体事务包裹防"半初始化"
- **双态配置**：`application-mysql.yml` + `docker-compose.yml`，一条命令切真实 MySQL；生产 profile 显式关闭演示种子与 H2 控制台
- **演示数据设计**：四笔订单覆盖全部状态（张伟-今日入住待办理/李娜-在住/王强-今日退房/赵敏-待支付）+ 1 条 LOS 规则，评委 5 分钟走完全状态流与拒单场景

### 亮点 7：LOS 收益管理约束层（Length Of Stay，业务深度）

- **问题**：酒店收益管理的核心诉求——国庆档"最少连住 3 晚"防止 1 晚散单占据稀缺房晚、旺季限制长住
- **方案**：
  - 表 `los_rule(room_type_id, start_date, end_date, min_nights, max_nights, remark)`——按"房型 × 日期段"约束连住晚数
  - 领域策略 `LosPolicy`（纯函数）：入住区间与规则日期段**重叠即生效**，多规则重叠取**最保守并集**（min 取最大、max 取最小）
  - 下单时在**锁库存之前**快速失败：`LOS_MIN_NOT_MET`(400，"需连住至少 N 晚") / `LOS_MAX_EXCEEDED`(400)
  - 房态接口透出 `minLosNights`，前端可提前告知客人连住要求
- **维度归属（诚实标注）**：行业标准中 LOS 挂在房价码（RatePlan）维度，与价格同属收益管理对象；本系统为单房价码（BAR-only）简化，规则直接挂房型，多房价码演进 = 价格与约束均挂 `rate_plan_id`
- **证明**：`LosPolicyTest` 8 例（无规则放行、非重叠忽略、部分重叠生效、Min/Max 违反与满足、多规则并集、默认约束）+ HTTP 2 例（拒单与放行、校验先于库存锁定）

### 性能基准实测（`mvn test -Dtest=BenchmarkTest -Dexcluded.groups=none`）

| 场景 | 结果 | 解读 |
|---|---|---|
| 串行下单 ×200（日期错开） | **262.7 TPS**，3.81 ms/单 | 业务代码单笔路径开销基线 |
| 并行 ×8 ×200（日期错开） | 19.7 TPS | **受 H2 单写者架构限制**（演示库特性），写事务在库层串行化 |
| 并行 ×8 ×200（同一日期段，行锁竞争） | 19.4 TPS | 与错开场景几乎相同 → 证实瓶颈在 H2 写串行化，而非业务行锁 |

> **如实说明与答辩口径**：H2 为单写者引擎，任何并发写都会被库层排队（这正是上面两个并行场景 TPS 几乎相同的原因）。生产 MySQL 为**多写者行锁**，不同日期段（不同库存行）的订单可真正并行写入，吞吐随连接数线性扩展；热点日期段仍由行锁串行化保证不超卖。**并发正确性不依赖吞吐**——由 ConcurrencyTest（10 线程抢 1 间恰 1 成功）与 DeadlockFreeTest（20 线程交叉锁无死锁）专项保证。如需真实并发吞吐数据，用 docker-compose 起 MySQL 后以 `--spring.profiles.active=mysql` 重跑同一基准即可。

## 四、答辩要点速查（面试官追问预案）

| 可能的问题 | 回答要点 |
|---|---|
| 为什么 Java 8 / Boot 2.7？ | 匹配目标企业存量体系（见 02 §2）；知情决策 + 迁移友好（javax→jakarta 即可升级 Boot 3） |
| 防超卖为什么不用 Redis/分布式锁？ | 单库行锁正确性第一、实现可讲清楚、与 MySQL 生产行为一致；热点场景演进路径已文档化（02 §5.4），量化阈值：**单行 TPS 预估 >5000 时切 Redis Lua + DB 兜底对账** |
| 加锁影响吞吐吗？能不能用乐观锁？ | **已实现双模式可切换**：optimistic=条件原子更新（零锁等待、受影响行数判冲突），与悲观锁各配同规格 10 线程并发测试证明不超卖；对照表与生产选择见 02 §5.3——低竞争用乐观、热点用 Redis Lua、行锁是最简正确基线 |
| 幂等靠什么保证？唯一索引是哪个？ | 三层防护：前端 `crypto.randomUUID()` 生成 request_id（每次下单动作一次、失败重试沿用）→ **`hotel_order` 表 `uk_request_id UNIQUE (request_id)` 唯一索引**（数据库最终防线，不过期不失效）→ 并发窗口由事务内二次检查 + DuplicateKey 回滚返回胜者订单兜底（见亮点 3） |
| 为什么并行基准 TPS 反而低（19 vs 262）？ | 如实回答：H2 是单写者引擎，并发写被库层串行化——这是演示库特性而非业务代码瓶颈；生产 MySQL 多写者行锁，错开日期可线性扩展（04 §三 有实测与解读） |
| 超时未支付订单怎么处理？ | 生产方案：Quartz 每分钟扫描 `PENDING_PAYMENT` 且 `created_at < now-15min` 的订单 → 状态机取消（释放库存）+ 通知；本演示版以手动取消演示同一状态机路径 |
| 支付回调如何保证幂等？ | 状态机已拒绝重复支付（409）；生产方案：支付流水表 `payment_transaction_id` 唯一索引，回调先落流水再驱动状态迁移，重复回调幂等命中 |
| 为什么不用状态机框架？ | 本场景 5 状态 7 迁移，枚举迁移表是零依赖的最简充分解；框架（Spring StateMachine 等）留到多事件源场景再引入 |
| 事务边界为什么放在 Service？ | 编排型用例（下单）用 TransactionTemplate 显式声明；Controller 只做参数校验与响应装配 |
| 幂等窗口过了怎么办（request_id 失效）？ | 唯一索引是数据库层最后防线，不会失效；前端键策略保证"每次下单动作一次" |
| LOS 为什么不挂在房价码上？ | 你（评审）说得对，行业标准中 LOS 属于房价码（RatePlan）维度；本系统是单房价码（BAR-only）简化故挂房型，已在 LosRule 注释与 02 §3.3 显式标注多房价码演进路径 |
| ROOM_TYPE 为什么叫房型不叫商品？ | 商品（Product）= 房型 × 房价码；房型是物理资源概念（库存归属），product 不该有 total_rooms。单房价码简化下房型兼任商品职责已显式标注（RoomType 注释、02 §3.2），演进 = product 表拆分 |
| 覆盖率只有 69%，够吗？ | 分层看：领域层 ~95%、配置层 100%（规则全穷举）；控制器/异常分支部分覆盖。集成测试驱动的金字塔 + 关键路径（防超卖/状态机/幂等/LOS）全覆盖是重点，盲目凑行数没有意义 |
| 如果评委问华住场景 | 见 01 §5：daily_inventory ↔ 中央库存/OTA 渠道分发，状态机 ↔ PMS Reservation，超时未支付自动释放是第一优先级生产改造 |
