## 一、项目答辩题

### Q1. 一句话介绍你的系统与关键决策

我用四步法交付这个一句话需求：**需求澄清 → 领域建模 → 实现验证 → 工程化交付**。澄清阶段把"酒店系统"拆出 7 个歧义点并逐条给假设（单店/含模拟支付/游客下单等）；建模阶段做了三个关键决策——库存粒度定为**房型×日期**（并发控制单元）、订单**显式状态机**（5 状态 7 迁移）、**幂等下单**（request_id + 唯一索引）；实现阶段 47 个用例全绿，含 10 线程并发防超卖与双模式（悲观/乐观）证明；交付阶段一条命令可跑、零外部依赖、文档截图录屏齐全。技术栈选 Java 8 + Boot 2.7 是匹配华住存量体系的知情决策。

### Q2. 为什么 Java 8 / Spring Boot 2.7？

三个理由：**① 匹配存量体系**——华住技术栈以 Java 8 + Boot 2.x + MyBatis 为主流，评审看代码零心智负担；**② 环境零风险**——本机原生 JDK8，现场演示不做任何环境改造；**③ 成熟度**——2.7.18 是 2.x 线的最终稳定版，"成熟框架"的字面最优解。同时我**主动坦白**：2.7 社区支持已结束，这是知情决策不是信息盲区——代码刻意保持迁移友好（领域逻辑与框架解耦、未用 Boot2 特有 API、包结构按"订单域/库存域"切分），升级 Boot3 只需换 starter 和 `javax→jakarta` 命名空间。如果华住正在推进 Java 17 迁移，我的代码结构可以直接承接。

### Q3. 防超卖怎么做的？怎么证明？

核心是**消除"查余量-扣减"之间的竞态窗口**。第一步是建模：库存拆成**房型×日期行**（`daily_inventory`，唯一约束 `uk_inventory(room_type_id, biz_date)`），并发控制单元 = 某晚某房型的可售量。第二步是事务内三步：`SELECT ... FOR UPDATE` **按日期升序**锁定全部占用晚（固定加锁顺序，杜绝交叉死锁）→ 锁内校验每晚 `sold + n ≤ total` → 扣减 + 落单 + 状态流水同事务提交，任一步失败整体回滚。**证明**：`ConcurrencyTest` 用 10 个线程同时抢仅剩 1 间的两晚房——断言"恰 1 单成功、9 单被 INSUFFICIENT_INVENTORY 拒绝、每晚 sold ≤ total 且最终 = total、库中仅 1 笔订单"。另外我还实现了乐观模式（`tryDeduct` 条件原子更新），两模式同规格测试，后面对比。

### Q4. 加锁影响吞吐，能用乐观锁吗？

**已经实现了，双模式可切换**（`app.booking.inventory-mode`）。悲观锁的冲突代价是排队等待（公平、确定）；乐观锁用**条件原子更新**：`UPDATE daily_inventory SET sold_rooms = sold_rooms + n WHERE id = ? AND sold_rooms + n <= total_rooms`——库存是计数器而非行替换，所以**不需要 version 字段**，WHERE 条件本身就是校验，单语句原子，冲突由受影响行数=0 判定，比版本号 CAS 更简。生产选择：**低竞争日期段用乐观**（零锁等待、吞吐更高），**热点日期（单行 TPS>5000）切 Redis Lua**（单线程串行化的内存版悲观锁）+ DB 兜底对账，行锁是最简正确基线。两个模式的正确性都有同规格 10 线程测试证明。另外说一个容易被忽略的点：锁粒度已经是房型×日期行、持有时间毫秒级，吞吐瓶颈通常先出现在连接池和网络，而不是这几把锁。

### Q5. 为什么库存粒度是房型×日期，而不是房型总房间数？

因为酒店卖的是**"某晚某房型的可售量"**，不是"某房型有多少间房"。如果只存 total_rooms，"今晚剩 0 间、明晚剩 2 间"这种跨日期库存状态就表达不了，预订跨晚订单的校验无从谈起。粒度定为房型×日期后，三个东西都自然挂在这个维度上：**并发控制的加锁单元**、**价格日历**（周末差异化定价）、**LOS 约束**（连住限制）。这也是真实酒店系统 CRS 的库存模型原型；扩展连锁多店时加一个 `hotel_id` 维度即可，模型不推翻。

### Q6. 状态机为什么不用框架？NoShow 怎么加？

本场景 **5 个状态、7 条迁移**，用枚举内置 `TRANSITIONS` Map 是零依赖的最简充分解：迁移表是唯一事实来源、未声明的迁移一律 409、纯领域对象可以直接单测穷举。状态机框架（Spring StateMachine 等）的价值在多事件源、复杂守卫编排的场景，这里引入是过度设计。**NoShow 的扩展**很简单：迁移表加一条 `CONFIRMED → NO_SHOW`（终态、释放库存），由"入住日未到店"的定时任务驱动——不需要改任何现有迁移。退款/改期不新增状态，用支付流水表和变更单承载，状态机保持单一职责。每次迁移都追加 `order_log` 流水（轻量事件溯源），时间线、审计、对账一个表搞定。

### Q7. 幂等怎么保证？唯一索引是哪个？

**三层防护**，各挡一种竞态窗口：**① 键来源**——前端每次"下单动作"生成一次 `request_id`（`crypto.randomUUID()`），失败重试沿用同一键、成功后清空，保证"一次动作一个键"的语义；**② 数据库最终防线**——`hotel_order` 表上的 **`CONSTRAINT uk_request_id UNIQUE (request_id)`** 唯一索引。它不过期、不失效，即使前端键丢失或被绕过，重复插入也会被数据库拒绝，这是幂等语义的最终保证；**③ 并发窗口处理**——事务内二次检查（悲观模式在拿到行锁后、乐观模式在扣减前）+ 撞唯一索引时的 `DuplicateKeyException` 处理：事务整体回滚（**含库存扣减**）→ 重读返回"胜者"已创建的订单。还有个细节：订单号撞 `uk_order_no` 与幂等冲突是两个不同场景，我在 catch 里做了区分——requestId 命中返回原单，否则判定订单号冲突、换号重试一次，不会把合法下单误判成 500。测试 A-02 证明：同 requestId 提交两次，同一订单号、库存只扣一次。

### Q8. 取消订单和提前退房的库存怎么释放？

两条路径，语义不同：**取消**只从占房状态（待支付/已确认）触发，同事务内释放**全部占用晚**的库存，和下单扣减对称地做完整性校验（锁定行数必须等于应释放晚数）；**提前退房**只释放**退房日之后的未住间夜**——退房当日及之前的间夜视为已消费。为什么这个很重要：如果没有提前退房释放，客人订 3 晚只住 1 晚，剩下 2 晚的库存会被"幽灵占用"永远不可售，房态和实际物理房态就漂移了。两个路径都有测试：A-11（取消后余量回升可再订）、A-20（3 晚订单当日退房，退房日之后两晚 sold 归零、当日保留）。

### Q9. LOS 是什么？为什么挂房型而不是房价码？

LOS = Length Of Stay，酒店收益管理的核心概念：**MinLOS**（国庆档最少连住 3 晚——防止 1 晚散单占据稀缺房晚）、**MaxLOS**（旺季限制长住）、同族还有 CTA/CTD（禁止某日入住/离店）。我的实现：`los_rule` 表按"房型×日期段"配置，`LosPolicy` 纯函数做重叠判定（入住区间与规则日期段有交集即生效），多规则重叠取**最保守并集**（min 取最大、max 取最小），下单时在**锁库存之前**快速失败，房态接口透出 `minLosNights` 提前告知客人。**关于维度归属，我如实说**：行业标准里 LOS 挂在**房价码（RatePlan）维度**，与价格同属收益管理对象——本系统是单房价码（BAR-only）简化，所以规则直接挂房型，这个简化已在代码注释和文档里显式标注，多房价码演进时价格与约束一起挂 `rate_plan_id`。

### Q10. 房型和商品是什么关系？为什么叫 ROOM_TYPE？

严格模型中：**商品（Product / Sellable Unit）= 房型 × 房价码**。"大床房-含双早-预付价"才是一个可售商品。房型是**物理资源概念**——库存归属它；价格、上下架、销售渠道这些是**商品层属性**。我的系统因为单房价码简化，房型与商品一对一退化，`room_type` 兼任了商品职责（物理属性 total_rooms 和销售属性 base_price 合一），这个兼任已经在实体注释和文档里显式标注。**为什么不能直接改名叫 product**：库存和物理房量必须挂在房型上，product 不该有 `total_rooms` 字段——改名会制造新的概念错误。正确演进是新增 `product` 表（room_type_id + rate_plan_id），把销售属性迁过去，房型回归纯物理资源定义。

### Q11. 为什么演示用 H2？切换 MySQL 要改什么？

演示场景选型的第一原则是**现场可靠性**：H2 文件库零外部依赖（评委现场可能无网、无 Docker）、`MODE=MySQL` 保证与生产同一套 SQL 和 FOR UPDATE 语义。**切换 MySQL 只改启动参数**：`--spring.profiles.active=mysql`——驱动已打进包、`docker-compose.yml` 一键起库、schema.sql 两库通用（一个细节：索引内联在 CREATE TABLE 里，因为 MySQL 8 不支持 `CREATE INDEX IF NOT EXISTS`）。生产 profile 还显式做了两件事：关闭演示数据种子（防止演示数据进生产库）、关闭 H2 控制台（防止未授权 SQL 入口）。

### Q12. 并行基准 TPS 反而低（19 vs 262），怎么解释？

如实回答：**H2 是单写者引擎**，任何并发写事务都在库层被串行化——证据就是两个并行场景（日期错开 vs 同一日期段）TPS 几乎相同（19.7 vs 19.4），瓶颈在 H2 的写串行化而不是业务行锁。这是演示库的特性，不是业务代码的问题：生产 MySQL 是**多写者行锁**，不同日期段的订单可真正并行写入，吞吐随连接数线性扩展。**并发正确性不依赖吞吐**——它由 ConcurrencyTest（10 线程恰 1 成功）和 DeadlockFreeTest（20 线程交叉锁无死锁）专项保证。如果需要真实并发吞吐数据，docker 起 MySQL 后以 mysql profile 重跑同一个 BenchmarkTest 即可，代码不用改。

### Q13. 支付回调幂等和超时未支付怎么处理？

**支付回调幂等**：演示版由状态机拒绝重复支付（409）保证语义等价；生产方案引入**支付流水表**，`payment_transaction_id` 唯一索引——回调先落流水再驱动状态迁移，重复回调命中唯一索引即幂等返回；回调还要做验签和金额核对（防篡改、防金额不一致）。**超时未支付**：Quartz 定时任务每分钟扫描 `PENDING_PAYMENT` 且 `created_at < now-15min` 的订单 → 走状态机取消（自动释放库存）+ 通知客人。扫描本身是幂等的——状态机保证重复扫描不会重复取消。我系统里这两处目前是手动/模拟形态，但状态机路径与生产方案完全同构，替换实现即可。

### Q14. 覆盖率只有 69%，够吗？

分口径看：**领域层 ~95%、配置层 100%**——所有业务规则（状态机迁移、日期规则、计价、LOS）都被穷举测试；被拉低的是控制器与全局异常分支。我的策略是**集成测试驱动的金字塔**：关键路径（防超卖、状态机、幂等、LOS）全覆盖 + 并发专项测试，而不是盲目凑行数。举个例子：给 DataInitializer 的周末价分支补两个单测，覆盖率能涨 2 个百分点，但对正确性保证没有任何增量——那是为了数字而数字。评审如果在意，我可以解释这个分层策略，比 95% 的假覆盖率更有说服力。

### Q15. AI 写错过什么？你怎么发现的？

诚实列几个真实的：pom.xml 注释里含 `--` 导致 XML 解析失败；MySQL 驱动坐标用成了过时的 `mysql-connector-java`；幂等竞态——并发同 requestId 重放可能先撞"房量不足"而不是返回原单；schema.sql 用了 MySQL 8 不支持的 `CREATE INDEX IF NOT EXISTS`；提前退房不释放剩余间夜库存；营收口径把未支付订单算进去。共 **14 项实质缺陷**。发现机制：**独立 code-review Agent 评审**（10 个角度并行扫 + 逐条独立验证）+ **机器可判的验证链**（编译 → 测试 → 真实浏览器验收），修复后全量回归。我的结论是：AI 写代码必须有验证闭环兜底——**"AI 写错 + 闭环抓住"这个组合，比"一次写对"更可信**，这也是 AI Coding 考题真正想看的。

### Q16. 第一优先级生产化改造是什么？

按**资损风险排序**：① **超时未支付自动释放**——现在要手动取消，真实场景超时订单会永久占房（资损）；② **鉴权 JWT**——手机号是弱凭证，查询接口有越权面；③ **支付流水表**——接真实支付网关的幂等前提；④ MySQL 切换 + 监控埋点（TraceId 贯穿、关键指标打点）；⑤ 库存热点演进（Redis Lua）。每一步都有明确的"为什么排在前面"的理由，而不是流水账。

## 二、酒店业务领域题

### Q17. 酒店中央库存（CRS）怎么和 OTA 渠道同步库存？

酒店中央库存系统（CRS——我系统里 `daily_inventory` 就是它的最小原型）是库存的**单一事实来源**，各渠道（携程/美团等）持有各自的库存副本。同步分两种模式：**直连渠道**（渠道通过 API 实时查价查房并下单，天然共享库存）和 **OTA 自有库存**（推送式分发：库存变化事件 → 渠道 API 更新 → 定期校准）。核心矛盾是多渠道同时卖会超卖，三种解法：共享同一库存池实时扣减（直连）、**渠道配额分配**（给每个渠道划库存份额）、余量推送 + 订单回灌 + 对账修复。设计要点：库存变化异步分发（MQ 削峰）、渠道库存水位告警（低于阈值主动补货/下架）、渠道订单回灌幂等（防重复占房）、日终对账任务修复漂移。华住体量下还要处理渠道 API 限频和部分渠道 10-30 分钟的生效延迟。

### Q18. PMS 是什么？和预订系统的边界在哪？

PMS（Property Management System）是**前台运营系统**：房态盘（哪间房脏/净/修）、入住退房办理、客账、夜审。预订系统管"**卖**"（库存、价格、订单），PMS 管"**住**"（到店后的运营）。交互边界：① 预订订单推送到 PMS 生成 Reservation；② PMS 的 CheckIn / CheckOut / NoShow 事件回传预订系统同步订单状态——**我的订单状态机里"办理入住/退房"动作位，对应的就是这些 PMS 报文位**；③ 房态双向同步：PMS 的物理房态（维修房、脏房）影响 CRS 的可售库存。华住体系还有个特殊点：自有酒店用华住 PMS，加盟店可能是第三方 PMS，所以需要一个**协议适配层**统一抽象（这也是我在方案里把入住/退房做成统一状态机动作的原因）。

### Q19. 房价码（RatePlan）模型怎么设计？

三维模型：**房价码（rate_plan）× 房型（room_type）× 日期（date）**。房价码是销售维度：BAR（门市价）、预付价（提前预订折扣）、会员价、协议价（企业协议）、OTA 专属价。每个"价码×房型×日期"单元格上有两样东西：**价格日历**（per date 的价格）和**限制（Restrictions）**——LOS（最少/最多连住）、CTA/CTD（禁止某日入住/离店）、售卖渠道、提前预订天数（如"提前 7 天可订"）。预订时价格引擎按**优先级链取最低可售**：协议价 > 会员价 > 预付 > BAR。实现上：`rate_plan` 主表 + `rate_plan_price(plan_id, room_type_id, biz_date, price)` + `rate_plan_restriction`。我系统里的 `daily_price` 和 `los_rule` 就是单房价码场景下的退化形态——文档里已显式标注这个演进关系。

### Q20. 酒店"超售"听说过吗？和防超卖矛盾吗？

听说过，而且**不矛盾**——这是两个层次的问题。真实酒店/航司有**主动超售（overbooking）**：行业 NoShow 率通常在 5%~10%，适度超卖是对冲未到店损失的收益最大化手段。超售比例按"预测 NoShow 率 ± 弹性"动态调，按房型/日期/渠道维度配置。我做的**防超卖防的是"意外超卖"**——超卖且客人全部到店是资损事故（违约、赔付、升级房型），这是底层正确性前提，主动超售是建立在正确库存记账之上的**收益管理策略层**。如果做主动超售，必须配套三件事：超售上限控制、到店前确认流程（提前一天确认降低 NoShow 不确定性）、满房预案（外送酒店协调、升级、补偿标准）。先保证"账不超卖"，再谈"策略性超卖"。

### Q21. 双 11 大促，酒店库存系统怎么扛？

分层设计，五步走：**① 热点识别**——用历史数据预测爆款（房型×日期，比如度假酒店的大促周末）；**② 热点库存前置**——Redis Lua 原子扣减作为前置闸门（单线程串行化），DB 做兜底与最终一致（异步落库 + 对账修复差异）；**③ 流量治理**——限量队列/排队机制保护下游，令牌桶限流，房态查询走短 TTL 缓存 + 大促期间锁价减少实时计算；**④ 降级预案**——库存接口降级为只读静态化、非核心服务熔断；**⑤ 监控对账**——扣减速率、对账差异、P99 延迟分位。实操经验点：先压测再放量、库存预留缓冲带、大促结束后全量对账。核心思想：**把流量峰值挡在内存层，DB 只做正确性兜底**。

### Q22. 华住会会员价怎么设计？

**会员等级（银/金/铂）× 房价码的动态定价**：会员价本质是 BAR 的折扣映射（如铂金 85 折），挂在价格引擎的优先级链上——系统对同一客人自动取最低可售（协议价 > 会员价 > 预付 > BAR），不需要运营为每个等级手工维护价格。实现要点：**① 身份注入**——报价请求携带会员等级（来自会员中心），价格引擎按等级注入折扣价；**② 权益类**（升房券、延迟退房）不放在价格里，走权益中心异步核销，避免价格链路复杂化；**③ 渠道冲突**——OTA 渠道价与会员价冲突时，用渠道限价策略（渠道订单不享受会员折扣，或享受但计入渠道结算差异）；**④ 审计**——会员价成交记录回流会员体系，用于等级核算和营销分析。

### Q23. 渠道价格一致性（Rate Parity）怎么保证？

OTA 合同里通常有**价差率条款**：自有渠道的价格不能低于 OTA 展示价，否则 OTA 会降权甚至下架酒店。方案核心是**中央价格库单向分发**：运营只维护一套价格（BAR/预付等），价格引擎按渠道费率/佣金换算生成各渠道价（如 OTA 佣金 15%，渠道价 = 底价 × 1.15），通过渠道 API 推送 + 渠道回读校验。监控侧：**价差监控任务**定期抓取各渠道展示价与中央库对比，出现倒挂（自渠价 < 渠道价）立即告警并自动修正。时效上，渠道侧有缓存，改价用"变更事件 + 渠道推送 + 兜底轮询"三层保障。我的系统里 `daily_price` 就是中央价格库的雏形，渠道分发是它的自然演进方向。

### Q24. 酒店临时调价，如何 5 分钟内生效到所有渠道？

链路是：**运营改价 → 中央价格平台写入 → 发布变更事件（MQ）→ 渠道推送服务调用各 OTA 房价接口 → 自渠缓存失效**。5 分钟目标的关键设计：**① 本地缓存 TTL 短**（自渠价格缓存按秒级/分钟级设计）；**② 推送优先于轮询**——改价事件驱动实时推送，定时轮询只是兜底；**③ 渠道 SLA 分级**——部分 OTA 本身有 10~30 分钟的生效延迟（接口侧限制），对这类渠道的承诺口径要分级（"最快 5 分钟、渠道最坏 30 分钟"），并在监控里分别统计；**④ 失败重试与补偿**——推送失败进重试队列，最终由每日全量价格对账兜底。这套"事件驱动 + 推送 + 对账"的三层结构，和库存分发是同一个模式，可以复用同一套基础设施。

### Q25. request_id 为什么前端生成，不应该后端生成吗？

**幂等键必须由动作发起方生成，前端生成是正确的，也是行业标准。** 幂等键的语义是"标识调用方的**一次业务动作**，并且**跨重试保持稳定**"——这个边界只有调用方知道。如果后端每次请求发新 ID：请求超时后客户端重试，重试拿到新 ID，后端当新订单处理 → **重复订单**，幂等直接破产。后端本质上无法区分"重试"和"第二次下单"。行业锚点：微信支付的 `out_trade_no`（商户订单号）、支付宝商户订单号、Stripe 的 `Idempotency-Key` 头——**全部由调用方生成**。

前端不可信的疑虑这样解决：① 键只做**去重**不做**鉴权**——真正执行者是数据库唯一索引 `uk_request_id`，键被篡改的最坏后果是订单被合并（往少的方向错），不是多扣钱；② 键缺失/不合法直接 400（`@NotBlank` 校验），进不了业务逻辑；③ 生产加固：命中已存在订单时校验订单归属同一用户，防"猜键看单"；④ 防御纵深可用"用户+房型+日期"哈希做服务端兜底键，但它**不能替代**调用方键——只能防同参数重复，防不了重试与二次下单的语义区分。我的实现时序：点击下单生成 `crypto.randomUUID()` → 失败重试沿用同一键 → 成功后清空。
